# CLAUDE.md

**Migration Safety Net for Divi 5** — a WordPress plugin that verifies Divi 4 → Divi 5 migrations: snapshot every page's rendered HTML before migrating, re-scan after, and report exactly what changed (DOM diff, noise-filtered). ET's built-in migrator predicts what *will* convert; this proves what *did* — including the clean bill of health.

This is **Dario's personal product venture** (storefront brand: **Tumil's Plugins**; Clicks Web Design, his employer, is not involved — the venture runs on personal accounts, support inbox tumilssupport@gmail.com). Goal: $300–800/mo. Free version on wordpress.org is the funnel; paid Pro add-on later via Freemius + the Divi Marketplace (70% cut).

**This plugin is the first of a portfolio, not the whole venture.** The idea queue for what ships next lives in its own repo: **`c:\wamp64\www\tumils-plugins-pipeline\README.md`** — 6 verified ideas ranked for build order, plus 14 killed lanes with the numbers that killed them. Read the killed table before proposing any plugin idea. Qualify new ideas with the `wp-plugin-idea-check` skill (live wordpress.org install counts + ratings), never from forum complaints.

## Hard constraints (from the spec — do not drift)

1. **Shared-hosting safe.** Loopback `wp_remote_get` for page capture. No headless browser, no exec, no external services.
2. **No build step.** Plain PHP + vanilla JS + hand-written CSS. Native WP admin UI (`WP_List_Table`). No npm, no React, no framework — same philosophy as Dario's themes.
3. **wordpress.org rules.** GPL v2+; the free plugin must be genuinely complete — no license gates, trials, or crippled code paths. Pro features live in a *separate* add-on plugin, never in this repo's .org build.
4. **Trademark + naming (settled by the round-1 review, do not drift back):** slug is `tumils-migration-safety-net-for-divi`, display name "Tumil's Migration Safety Net for Divi 5", text domain = slug. A distinctive brand word must come FIRST and the "Divi" trademark only after "for" — a name that opens with the generic description is what got the submission pended. Prefix everything `tumils_msn_` / `Tumils_MSN_` / `TUMILS_MSN_` (the old `msn_` was rejected: under 4 chars and reads as Microsoft Network). This covers classes, constants, hooks, nonces, asset handles, the localized JS object, DB table, options, the uploads storage dir, filters, and CSS classes.
5. **The diff engine ships with tests.** Fixture-based (`tests/` with real HTML fixtures + a plain `run.php` runner — no framework). False positives are the product's death; the normalizer is where the accuracy lives.

## Verified ground truth (don't re-research)

- Divi 4 content: `[et_pb_*]` shortcodes in `post_content`. Divi 5: `<!-- wp:divi/* {json} -->` block comments with a `builderVersion` attr (confirmed against a real Divi 5.2.1 DB).
- Divi 5 mostly *kept* `et_pb_*` CSS classes but changed the layout engine (float columns → flex/grid). Breakage is behavioral, not just renamed selectors — which is why the product measures rather than pattern-matches.
- Local Wamp: MySQL client at `c:\wamp64\bin\mysql\mysql8.4.7\bin\mysql.exe`, root/no password.
- **Real D4→D5 migration noise patterns (Task 11, confirmed via side-by-side screenshots of a real ET migration) — all handled in `MSN_Normalizer`:** D5 adds `et_block_*` marker classes almost everywhere with no visual effect; drops the `et_pb_gutters<N>` and default `et_pb_text_align_left` classes with no visual effect; adds a bare `et_pb_module` marker inconsistently; drops the `et_pb_with_background` toggle class and D4's empty-suffix `et_pb_divider_position_` in favor of an explicit `_top`; and D5 repeatedly unwraps/rewraps plain `<span>` text and consolidates a blurb module's icon-wrapper + text-wrapper divs into one, which — left unhandled — makes the tree differ's positional alignment misfire and turn one real change into a cluster of noise (fixed by unwrapping both at normalize time, not by touching the differ's alignment).
- **A real, confirmed D5 regression:** the blurb module's icon glyph does not render at all post-migration (icon markup is simply absent) — correctly caught by the differ as a `removed` hunk.
- **Snapshot HTML lives on disk, not in the DB:** `uploads/tumils-msn-snapshots/<run_id>/<url_hash>.html`; the custom table is only an index (url, url_hash, content_hash). So a DB restored without `wp-content`, a moved uploads dir, or pruned files leaves index rows whose files are gone — and until 2026-08-24 that combination diffed empty-vs-empty and reported **"verified clean"**, the exact lie the product exists to prevent. `Store::get_html()` now returns `false` (not `''`) for unreadable, and `Compare::missing_snapshot_hunks()` turns it into one structural `missing-snapshot` hunk. Covered by tests/test-compare-gaps.php and drilled against the real D4 data.
- **`removeAttribute()` cannot remove a namespace declaration or a reserved `xml:*` attribute** (measured on PHP 8.4 / libxml 2.11.9): it returns false, `hasAttribute()` also returns false, so the failure is invisible — and a following `setAttribute()` appends a SECOND copy. The normalizer's attribute-order rebuild hit this on any page with inline SVG, canonicalizing `<svg xmlns=".." xmlns=".." xml:space=".." xml:space="..">`, poisoning the content hash, and leaving those attributes pinned in source order so an order-only difference produced unequal canonicals with zero hunks — a synthetic `opaque` hunk on an unchanged page, i.e. the false positive the spec calls fatal. Fixed by removing the attribute *node* (`removeAttributeNode`), which does work on them: 6 distinct canonicals across 120 permutations before, 1 after. Covered by the inline-SVG cases in tests/test-normalizer.php.
- **wp-admin declares `line-height` in em, which computes to a length on the parent and inherits as that length.** A 48px glyph in the plugin's clean-verdict hero therefore got an 18.2px line box and painted over the sentence beneath it. Any oversized glyph in this UI needs an explicit `line-height`.
- **The Divi Marketplace sniffer runs WPCS 2.x, not 3.x — so `%i` fails review even though it is valid.** `$wpdb->prepare()` gained the `%i` identifier placeholder in WP 6.2 and WPCS 3.x accepts it silently; WPCS 2.3.0 calls it `PreparedSQLPlaceholders.UnsupportedPlaceholder` **and** then miscounts the remaining placeholders, so one `%i` also invents an "Incorrect number of replacements" warning on the next query. Both were measured on this file, not inferred: WPCS 3.4.1 reported zero, WPCS 2.3.0 reported the exact two errors ET sent. Interpolate `$wpdb->prefix` table names and reserve placeholders for values — that form is clean on both. WPCS 2.3.0 needs PHP ≤ 8.1 to run (8.4 aborts it with a nullable-parameter deprecation inside `PHPCSHelper`).
- **A known blind spot, not a bug:** a module's background *color* (e.g. a CTA/promo module) can visibly change between D4 and D5 while being completely invisible to this tool, because it's expressed only via generated CSS in a `<style>` block — which the normalizer intentionally strips as request-to-request noise. Any visual regression that's *purely* CSS-driven (not reflected in an inline `style=` attribute or a class name) will not be reported. This is inherent to the "no headless browser" constraint, not something a normalizer rule can fix.
- Divi 5's "Divi 5 Migrator" admin page (`admin.php?page=et_d5_readiness`) only detects pages as convertible if they carry postmeta `_et_pb_use_builder = on` — a page created via `wp post create` with raw `[et_pb_*]` shortcode content will render fine but won't show up in the migrator's compatibility scan until that meta is set.
